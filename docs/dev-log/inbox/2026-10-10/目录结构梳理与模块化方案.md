# 目录结构梳理与模块化方案

- 日期：2026-10-10
- 类型：设计
- 分支 / 提交：refactor/layering `9421704c`（未提交）

## 问题
重新梳理各目录结构和功能，看怎么调整，让后续 stats 等功能能更方便地接入。

## 结论 / 回答
- 现状：目录已经分层，但依赖方向还没有理顺。`core/` 名义上是基础设施，实际却在向上依赖：core→features 24 处、core→agents 23 处、core→runtime 12 处；runtime→agents 9 处、quota→agents 2 处
- 根因：设置（`prefs.js` / `actions.js` / `effect-router.js` / `ipc.js`）、i18n（两个文件共 12k 行，含 7 种语言）、托盘 / HUD / Dashboard / 设置侧栏都是集中硬编码的注册点。以 quota 为例，`src/quota/` 之外还有 35 个文件提到它；stats 照现在的方式接入，也要改差不多这么多文件
- 方案：保持现有顶层目录，新增「模块契约」。每个模块用一个 `module.js` 声明 prefs 片段、validators、effects、ipc、i18n、托盘分组、HUD 分段、Dashboard 分段、设置 tab，以及 `create(services)`；新增 `src/app/` 承接从 `main.js` 拆出来的组合根（services / 模块清单 / 贡献分发 / 生命周期）；`core/` 只保留注册表引擎，不 require 任何模块；ui 各窗口只负责渲染「内置项 + 模块贡献项」，模块的渲染脚本由 preload 下发列表后动态插入 `<script>`（现有 CSP 是 `script-src 'self'`，允许这样做）
- 分阶段：P0 由结构侧先建契约和 4 个展示扩展点，用 quota 作样板迁移；P1 stats 按契约接入；P2 逐个迁移 recap、telegram / feishu / slack / discord、themes / accessories、remote-ssh，清空 core 的向上依赖；P3 做 agents 适配器（layering §4.1）并按模块拆分 i18n；P4 整理 scripts / tools 等杂项目录
- worktree 分工：P0 改动的正是 menu / hud / settings / effect-router / main，由结构侧独占；stats 侧在 P0 合并前只写 `src/stats/` 内部

## 追问（同日）：这套做法属于哪种架构思想，是否适合"持续收纳开源工具"

### 问题
用户问：与 DDD 同层的其他思想有哪些、哪种适合 my-desktop-aide；预想后续持续收纳改造各种开源工具，每种工具的纳入都要独立、不影响既有 agents/stats 功能。

### 结论 / 回答
- 定名：本项目的架构思想组合 = **端口-适配器（六边形）为纲 + 微内核/插件为形 + 防腐层为闸 + 模块化单体边界强制为纪律 + 舱壁隔离为容错 + 声明式接入（descriptor/module.js）为接入体验**。与上面那版 P0–P4 方案是同一件事的两种表述，不需要引入新机制
- 判据（用户诉求可测化）：① 边界是否被测试强制；② 加一个工具时内核文件是否零改动；③ 一个工具挂掉是否波及其他；④ 外部工具的概念是否只存在于它自己的适配器内
- 明确不采用：微服务（Electron 单机宿主）、事件溯源 / CQRS（隐私红线禁止记录 prompt/路径/内容，没有完整事件日志这个前提）、DDD 战术模式全套（本项目核心是集成 + 编排 + 呈现，不是业务规则密集领域；DDD 战略部分即"限界上下文 + 统一语言"仍有价值）
- 三档纳入策略（按代价递增）：① 只读它的 CLI / JSON / 日志 → 适配器归一；② 用它的官方扩展点（plugin / hook / extension）注入，即现状做法；③ 才 fork，且差异面最小、放在独立仓库，内核不得出现该 fork 的特判
- 可落地红线：新增一个工具应只触碰有界文件集 —— `src/agents/<id>/descriptor.js`（+ 可选 `adapter.js`）、`src/agents/registry.js` 一行、`hooks/<id>/**`、`src/features/<name>/module.js`（模块契约落地后）、`test/agents/<id>/` 与 `test/hooks/<id>/`、i18n / 素材 / docs；**禁止**改 `src/runtime/**`、`src/core/**`、`src/ui/**` 的既有逻辑
- 现状缺口：`registry.js` 仍是手工 `require` 列表（可接受，注册表是唯一允许的加法面）；`test/repo/` 目前没有分层/边界强制测试，`readme-agent-lists.test.js` 是同类的"有界清单可测"先例，可照此加 `test/repo/layering-boundaries.test.js`（断言无跨模块 require、`runtime/` 与 `core/` 无 `agentId ===` 字面量分支）
